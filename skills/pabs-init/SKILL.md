---
name: pabs-init
description: Connect this conversation to an existing Pabs product or establish a new product’s Brief and strategy. Use for setup or reconnection, not to regenerate an existing strategy.
---

Pabs is the product owner and design lead for the product the person is working on. The plugin’s account connection is separate from project selection. Sign-in does not select a project, authorize unrelated work, or grant access to local folders or other connected services.

Call `connect_pabs_project` with one new UUID `request_id` and a short `project_label` for this conversation. This is the first Pabs call of setup, before reading files or anything else. It returns `authorization_url` and `confirmation_code`. Show the link and the code, and tell the person to choose the product on that Pabs page (an existing product or a new one) and to connect only if the page shows the same code. Present its Pabs `introduction` once, unchanged, while they do, and follow its current `usage_orientation` before proposing credit-consuming work. Then stop and wait for the person.

The person chooses the product in Pabs. Never choose it for them, and never infer it from a folder, workspace, repository or chat name, even when one looks like an obvious match. When they say they connected, call `connect_pabs_project` again with the SAME `request_id`. `status: connected` returns the `project_ref` and whether it is an existing or new product; `awaiting_person` means they have not finished, so show the link again without starting another request. Retain the `request_id` for retries and the returned `project_ref` throughout setup and later work. Include it on every project tool call; there is no account-wide active project.

If `connect_pabs_project` is not among your available tools, load the Pabs plugin's tools by that exact name through the host's tool loading. If it still is not available, say that the Pabs connection did not load in this chat and ask the person to open a new chat. Do not inspect plugin files, run commands, use a terminal or reach Pabs any other way to work around it.

While the person connects, read `pabs_guidance` with reference `initialization`. Use the remote-connector path in that guidance: do not run a shell installer, call local `pabs_initialize`/`pabs_connection`/`pabs_project_context`, or ask for credentials. If the host requires sign-in, use its Connect flow.

Call `get_client_status` with that reference and follow `next_operation`. An unfinished new product follows `get_setup_contract`, saves its supported foundation with `save_product_foundation`, and completes with `complete_initialization`. For an existing product, read `get_project_onboarding`: understand `work_snapshot`, current Jobs and delivered results alongside the saved verdict/date, Pulse, blockers and steps before forming the closing. Follow explicit Job/mission links and actual next actors. Inspect the relevant Job with `get_active_work` by ID when needed; its general builder handoff list is not the full project queue. Continue existing work instead of restarting its saved recommendation or recreating an artifact. A delivered requirement waiting for review needs the person’s decision, not more implementation. Do not assume unrelated Jobs block every step or that activity proves an outcome. Explain an honest waiting state when no useful action or support is available. Never execute, retry, approve, schedule or regenerate work merely to finish init. If your actual work materially changes the picture, refresh onboarding once before closing, without polling.

If a save’s outcome is unclear, read status using the SAME reference before trying again. Never start another setup to recover a save. Read and follow returned corrections, evidence limits, billing orientation and onboarding choices. A later visit to a product originally created through this plugin is an existing-product resumption, not another new setup.

Apply the canonical Pabs reasoning and entry-mode-specific closing guidance returned by the server. A new project presents `onboarding.first_take` unchanged. For an existing product, synthesize its current scenario from the strategic context, latest Pulse, current Jobs and results, pending requests and next actors, using `first_take` as grounded orientation rather than a mandatory script. Distinguish the saved verdict from your current contextual read, preserving any quoted Pabs-authored messages exactly. Offer only useful support for what can move now, or explain the waiting state. Use only evidence available through this conversation, user-provided material, connected services and folders the host actually permits. Do not invent project access or require a local folder for a product that can be understood from other evidence. A saved foundation does not mean its blockers are resolved, its design guidance is active, or routines are scheduled.

For subsequent product work use the `pabs` skill; for interface or design-guidance work use `pabs-design`.
